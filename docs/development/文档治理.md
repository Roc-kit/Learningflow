# Learningflow 文档治理

本文定义长期文档的职责、事实源、拆分与归档规则。目标是降低人工和 AI 开发时的无关上下文、重复维护和历史噪声。

## 1. 基本原则

1. 一个长期文档只承担一个明确职责。
2. 当前有效规则与历史过程分离；主文档描述“现在成立什么”。
3. 同一事实尽量只有一个权威来源，其他地方使用链接或短摘要。
4. 文档长度只是治理信号；主题混杂、重复或冲突时，即使不长也应拆分。
5. AI 按 `AGENTS.md` 路由按需读取，不为了建立上下文遍历整个仓库。

## 2. 文档职责

- `AGENTS.md`：多数开发任务都必须知道的稳定规则与文档路由。
- `PROJECT_STATE.md`：当前阶段、已验证事实、正在做什么、下一步。
- `DECISIONS.md`：长期关键选择以及为什么这样定。
- `docs/product/`：当前产品范围、业务概念和真实使用流程。
- `docs/architecture/`：当前架构、数据边界和技术工作基线。
- `docs/development/`：Git、测试、文档等工程治理。
- `docs/archive/`：被取代但仍具有追溯价值的正式文档。
- `resources/raw/`：本机原始聊天、AI 思考、外部原文；不进入 Git，不是现行事实源。

默认不为每个聊天窗口新增 handoff 文档。跨会话需要继续的当前状态进入 `PROJECT_STATE.md`；稳定结论进入职责对应的产品/架构文档。

## 3. 当前事实与历史过程

规则变化时采用：

```text
旧结论被推翻
→ 直接修改权威主文档
→ 如旧结论仍值得追溯，再归档或依赖 Git 历史
```

禁止：

```text
旧结论继续保留
+ 文末追加“最新改成……”
+ 再追加“现在又改成……”
```

调试命令、一次性日志、聊天流水和浏览器操作过程不进入长期产品文档。

## 4. 长度规则

### `AGENTS.md`

- 目标不超过 300 行；
- 接近 300 行时优先把专题规则下沉到 `docs/`；
- 不写成项目百科。

### 普通活跃 Markdown

- 目标不超过约 800 行；
- 超过 800 行时检查是否存在可独立演进主题；
- 超过 1500 行原则上拆分；
- `docs/archive/` 和 `resources/raw/` 不按此阈值机械拆分。

## 5. 何时必须拆分

满足任一条件时应拆分或重构：

1. 一个活跃文档长期维护多个独立业务域；
2. 当前规则、历史讨论、调试过程和已废弃方案混在一起；
3. 局部任务通常需要读取大量无关章节；
4. 同一主题在文档内部存在相互冲突的“当前说法”；
5. 只能依靠不断在末尾追加新结论来覆盖旧内容。

拆分后保留稳定入口或索引，不让调用方猜文件位置。

## 6. 版本化设计文档

当前 `docs/product/真实学习流程.md`、`docs/architecture/系统架构.md` 由正式建仓前的 v0.2 / v0.1 设计收口而来，已经改用稳定文件名。

以后如果只是细化同一现行方案，直接更新权威文档，不机械创建 `v0.3/v0.4/...`。只有需要保留一个明确、可比较的阶段快照时才复制到 `docs/archive/`，当前入口文件名保持稳定。

## 7. 原始材料

原始对话、截图转录、AI 思考、外部文章全文等只作为证据。它们可以很长，也可能包含已经被推翻的观点，因此：

- 默认不进入 Git；
- 默认不加载到新会话；
- 需要追溯某个决定来源时再定向读取；
- 一旦结论收口，应进入产品/架构/决策文档，而不是让原始聊天继续承担“记忆库”职责。

## 8. 每次修改长期文档时检查

1. 新内容属于哪个权威事实源；
2. 是在替换旧结论，还是仅仅追加；
3. 是否造成跨文档重复或冲突；
4. 是否需要把已失效内容归档；
5. `docs/README.md`、`AGENTS.md`、`PROJECT_STATE.md` 是否需要同步路由或状态。
