# Learningflow 项目管理

Learningflow 当前是单人主导、AI 深度参与的早期项目。项目管理的目标是：**让任何新会话快速知道现在做什么，让明确需求有追踪锚点，让历史过程交给 Git，而不是维护一套复杂流程。**

## 1. 四个层次各管什么

```text
PROJECT_STATE.md
    当前阶段 / 已验证事实 / 下一步

GitHub Issue（建立远端后）
    明确 Bug / Feature / 可验收任务

GitHub Discussion（工具和仓库支持时）
    开放式研究 / 产品方案比较 / 尚未决定是否实施的方向

Git commit / checkpoint
    已经实际落地的代码与文档历史
```

不要用每个聊天窗口一份 handoff 文档代替这些事实源。

## 2. 当前 Milestone

### M0：真实交接闭环

目标：证明“ChatGPT 教学 ↔ Learningflow 网页练习”在真实设备上可用。

最小范围：

```text
教学材料
→ 3 道网页题
→ 草稿保存
→ 交卷
→ 结构化结果包
→ 返回同一教学上下文继续教学
```

M0 不要求完整 OCR、知识图谱、复习算法和后台管理系统。

### M1：日常记录可用

范围：学生/Test-Real 隔离、任务、作业照片、压缩归档、OCR/修订、最小课程结构。

### M2：英语教学闭环

范围：提示、判分、诊断、Learner State、复习、MCP/API 与英语 Subject Pack。

### M3：持续运行可用

范围：后台调度、企业微信、日报/周报、基础教学反思、工具经验与恢复能力。

M1/M2/M3 的详细验收仍以 `docs/architecture/系统架构.md` 为准；这里不复制完整规则。

## 3. 什么时候建 Issue

建立 GitHub 远端后，满足以下任一条件就适合建 Issue：

- 明确 Bug，能描述现象和期望；
- 明确 Feature，能给出验收结果；
- 一个任务预计跨多个会话或有真实设备验收；
- 问题可能独立复发，需要长期追踪。

不强制为这些内容建 Issue：

- 一句话想法；
- 纯开放式研究；
- 尚未决定是否实施的方案比较；
- 一次性小型文档修正。

## 4. 一个任务如何流转

```text
发现问题 / 提出需求
→ 判断是 Discussion 还是 Issue
→ 明确本次验收边界
→ 实施
→ 针对性测试 / 真实设备验证
→ commit / checkpoint
→ 更新 Issue 状态
→ 如果项目阶段变化，再更新 PROJECT_STATE.md
→ 如果产生长期取舍，再更新 DECISIONS.md
```

Issue 是追踪锚点，不是实施授权本身；用户还在讨论时，不因为 Issue 已建立就自动开始修改产品行为。

## 5. Issue 内容保持简洁

优先写：

1. 用户看到的问题 / 想达到的结果；
2. 真实使用场景；
3. 验收条件；
4. 必要时附原始截图、日志或设备信息。

技术根因、实现方案、测试结果在分析和完成后补充，不让大段代码细节淹没产品问题。

## 6. 当前阶段的任务优先级

优先级按对核心闭环的影响判断，而不是按模块“是否完整”：

```text
P0  会导致真实学习数据错误、串学生、丢作答、把提示后答案当独立掌握
P1  阻断 M0/M1 当前主流程
P2  明显影响孩子/家长日常使用体验
P3  优化、研究、未来扩展
```

Stage 0 不因为某个后台模块“还没有”就自动提高优先级。

## 7. 项目状态收口

只有以下变化才需要更新 `PROJECT_STATE.md`：

- Milestone 阶段推进；
- 当前正式运行环境/技术基线变化；
- 关键模块从“设计”变成“已实现/已验证”；
- 下一步主线发生改变；
- 某个重大阻塞出现或解除。

普通 commit、每个小 Bug、完整命令流水不写入 `PROJECT_STATE.md`。

## 8. 远端尚未建立时

当前本地仓库先使用：

- `PROJECT_STATE.md` 管当前主线；
- Git commit 管实施历史；
- `DECISIONS.md` 管长期决策。

GitHub 仓库建立后再启用 Issue / Discussion / Project，不需要为了形式在本地模拟一套假的 Issue 文件夹。
