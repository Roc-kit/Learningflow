# Learningflow：ChatGPT 的长期学习操作系统

更新日期：2026-09-12

状态：产品 / 架构定位基线。

Learningflow 不再以“再做一个 AI 学习产品”为目标。它的定位是：

> **给 ChatGPT 提供一个可长期运行、可追溯、可调度的学习操作系统。**

ChatGPT 继续负责它本来就擅长的部分：理解、对话、语音、讲解、追问、生成和推理。Learningflow 只补齐单次聊天天然不适合长期承担的能力：学生身份、学习事实、Evidence、历史状态、复习调度、教学协议、后台任务和专用输入输出。

## 1. 最核心的两条数据方向

Learningflow 与 ChatGPT 之间最重要的不是“页面跳转”，而是两条稳定的数据通路：

```text
Learningflow
    │
    │  现在应该知道什么？
    ▼
Learning Context
    │
    ▼
ChatGPT
    │
    │  刚刚真实发生了什么？
    ▼
Learning Evidence
    │
    ▼
Learningflow
```

可以简化成：

```text
Context → ChatGPT → Evidence
```

长期系统围绕这个闭环不断运行。

### 1.1 Context 不是数据库 dump

ChatGPT 每次教学不需要读取全部历史，而需要“当前决策真正相关”的上下文，例如：

```text
学生
当前任务 / 当前教材范围
最近相关作答
已确认的能力
证据不足的地方
活跃错因候选
到期复测
近期已经用过的题
本轮教学目标
必要约束
```

Context 应该按任务裁剪、带来源、带新鲜度，而不是把整张表或全部聊天塞给模型。

### 1.2 Evidence 不是模型总结

教学结束后，Learningflow 最优先保存的是事实：

```text
问了什么
孩子实际回答了什么
文字 / 语音 / 页面 / 纸笔
回答前有没有提示
是否修改过答案
什么时候发生
评价依据是什么
取得的记录到底是原文、转写还是摘要
```

“孩子掌握了第三人称单数”属于后续分析，不是原始 Evidence。

## 2. ChatGPT 与 Learningflow 的职责边界

### 2.1 ChatGPT 负责交互智能

默认由 ChatGPT 完成：

```text
理解孩子的问题
自然语言 / 语音互动
解释概念
举例
追问
生成题目
判断何时需要验证
根据回答调整讲法
决定是否继续、回退或换角度
```

Learningflow 不再建设一套平行的通用聊天老师来复制这些能力。

### 2.2 Learningflow 负责长期运行

Learningflow 负责：

```text
身份与数据范围
课程 / 任务 / 材料事实
Evidence Ledger
Assessment 事实
Learner State 派生与版本
Review / Scheduler
Teaching Reflection
后台任务与通知
专用 Activity
工具能力发现与经验
审计与恢复
```

一句话边界：

> **ChatGPT 决定怎么教；Learningflow 负责让教学有记忆、有证据、有后续。**

## 3. 逻辑分层

```text
┌──────────────────────────────────────────────┐
│ ChatGPT                                     │
│ 对话 / 语音 / 推理 / 教学 / 生成 / 决策       │
└──────────────────────┬───────────────────────┘
                       │
              Teaching Skills
                       │
                 MCP / Tools
                       │
┌──────────────────────▼───────────────────────┐
│ Learningflow Runtime                        │
│                                              │
│ Context Service      Evidence Ledger         │
│ Session / Assessment State                  │
│ State Compiler       Review Scheduler        │
│ Teaching Reflection  Capability Registry     │
└───────────────┬──────────────────┬───────────┘
                │                  │
         Activity Adapters     Background Workers
                │                  │
        Web / Media / Forms    Review / Report /
        Recording / Upload     Notify / Recompute
```

这里的 “Skill” 是逻辑概念，不绑定某个具体 ChatGPT 产品功能。

## 4. Teaching Skill 是协议，不是另一个 Agent

Teaching Skill 只用于那些**流程纪律会改变 Evidence 含义**的教学动作。

例如普通解释：

```text
孩子：为什么 does 后面不能用 likes？
GPT：直接解释
```

不需要为了“系统化”强行进入 Skill。

但如果现在要验证是否真的理解，则需要 Assessment Skill：

```text
进入验证
→ 一次一题
→ 问完停下
→ 等真实回答
→ 记录回答前提示
→ 先保存回答事实
→ 再评价 / 讲解
→ 决定继续验证还是退出
```

因此 Skill 的本质是：

```text
Teaching Protocol
+ Tool Usage Rules
+ Evidence Semantics
```

而不是：

```text
新的聊天机器人
新的长期记忆系统
新的模型
```

### 4.1 Skill 的宿主实现可替换

同一逻辑 Skill 未来可以实现为：

- ChatGPT 可安装的 Skill / Plugin；
- 系统提示中的稳定教学协议；
- MCP 工具说明与工作流；
- 自有编排服务中的 policy；
- 其他未来宿主提供的等价能力。

业务文档使用 `Assessment Skill`、`Review Skill` 等逻辑名称，不把当前某一种产品 API 当作永久架构。

## 5. Learning Context：给 ChatGPT 的“工作记忆包”

Learningflow 最关键的读接口之一应该是类似：

```text
get_learning_context(...)
```

它不是返回全部学生档案，而是根据当前任务生成一个有预算的 Context Packet。

建议逻辑结构：

```text
LearningContext
├── student_scope
├── current_goal
├── current_material
├── recent_relevant_evidence[]
├── supported_capabilities[]
├── uncertain_capabilities[]
├── active_misconception_hypotheses[]
├── due_checks[]
├── recently_asked[]
├── teaching_notes[]
└── constraints
```

M0 不要求这些字段全部实现。关键是提前确定：

> ChatGPT 获取长期记忆时，优先读取一个经过筛选的学习上下文，而不是自己遍历原始数据库。

### 5.1 Context 必须保留不确定性

例如应该表达：

```text
does 后动词原形：
  最近一次独立验证：无
  guided practice：2 次正确
  delayed evidence：无
```

而不是简单写：

```text
mastery = 80%
```

## 6. Evidence Ledger：系统长期最重要的资产

长期最可靠的资产不是某一版 Learner State，而是可重新解释的 Evidence。

```text
LearningSession
  ├── TeachingEvent
  ├── AssessmentRun
  │     └── AssessmentItem
  │            ├── LearnerResponse
  │            └── AssessmentRevision
  └── ActivityResult
```

以后作业照片、OCR、朗读、作文等都继续进入同一 Evidence 层，而不是各做一套独立“掌握度”。

### 6.1 事实与推断分开

```text
事实：
孩子回答 "likes"

分析：
本题错误

诊断假设：
可能没有理解 does 后用原形

状态推断：
该规则独立应用证据不足
```

四层不能压成一个字段。

## 7. MCP / Tools 是系统调用层

如果使用操作系统类比，MCP / Tools 最接近“受控系统调用”：ChatGPT 不直接修改数据库，而通过明确业务操作读写长期系统。

第一阶段应该保持工具数量少，语义强。尤其 ChatGPT 是主教学 Runtime 时，不要让一次自然教学被数据库式的 `create row → update row → close row` 工具链打断。

建议围绕五类能力：

```text
Context
  get_learning_context

Evidence
  record_assessment_run

Activity
  create_specialized_activity
  get_activity_result

Later
  record_teaching_event
  get_due_reviews
  record_teaching_reflection
```

`record_assessment_run` 可以一次保存一小段真实问答，也可以在宿主能力允许时增量写入。服务端自己拆成 AssessmentRun / Item / LearnerResponse / AssessmentRevision；这些内部表不要求一一暴露为 ChatGPT 工具。

不要把每张表都暴露成一个 MCP CRUD 工具，也不要提供任意 SQL。

工具 Contract 应表达业务事实，而不是数据库实现。

## 8. Activity Adapter：只补 ChatGPT 不擅长的输入输出

Web 的定位进一步明确为 `Activity Adapter`。

它解决的是交互媒介问题，而不是教学智能问题。

适合调用 Adapter 的场景：

- 上传学校作业照片；
- 在图片上圈选 / 标注；
- 匹配、排序、拖拽；
- 多空位复杂题；
- 长作文编辑和版本比较；
- 需要保留原始音频的朗读；
- 需要严格控制答案暴露的独立测验；
- 未来传感器或其他特殊输入。

统一模型应该是：

```text
ChatGPT
→ 判断需要某种 Activity
→ create_specialized_activity
→ Activity Adapter 负责采集
→ Server 保存事实
→ ChatGPT 取得结果
→ 继续教学
```

如果 ChatGPT 自身未来能自然承载某种 Activity，就可以取消外部 Adapter，不需要维护“必须网页化”的产品边界。

## 9. Background Runtime：让学习跨越聊天会话继续存在

ChatGPT 对话结束后，Learningflow 仍然运行：

```text
延迟复测到期
→ Scheduler 产生 Review Intent

作业截止时间将到
→ Worker 检查状态
→ 必要时通知家长

新的 Evidence 到达
→ State Compiler 标记相关状态需要重算

一周结束
→ 汇总教学动作 + 延迟表现
→ 产生 Teaching Reflection
```

这些后台任务的产物最终仍然是为了下一次 ChatGPT 教学：

```text
今天有一个到期复测
上次两次都需要规则提示
三天前的独立证据仍为空
建议先用一道新场景题验证
```

## 10. Learner State 是缓存 / 编译结果，不是历史真相

长期架构应把 Learner State 看成从 Evidence 编译出来的读模型：

```text
Evidence Ledger
      │
      ▼
State Compiler
      │
      ▼
Learner State Snapshot
```

以后无论使用：

- 简单规则；
- 间隔规则；
- BKT；
- IRT；
- FSRS；
- LLM-assisted inference；

都可以替换 Compiler，而不用修改历史真实作答。

这也是未来与 LSL 等 learner-state interchange format 对接的合适位置。

## 11. 家长端与维护端为什么仍需要独立界面

“ChatGPT 是主入口”特指**孩子的教学体验**，不等于所有 UI 都消失。

以下任务天然更适合管理界面：

```text
家长查看今天任务
确认 OCR
纠正题目识别
查看周报
处理通知异常
修改学生设置
查看 Evidence 追溯
维护教材与课程映射
测试 / Real 数据切换
系统运维
```

这些界面服务于管理和校正，不与 ChatGPT 争夺“老师”这个入口。

## 12. 学科包的职责也随之更清楚

Subject Pack 不需要自己实现一个完整英语 Tutor。

它主要给 ChatGPT / Skills / Runtime 提供：

```text
Concept vocabulary
教材范围
前置关系
题型约束
评分规则
常见错因候选
诊断提示
教学策略候选
Evidence 解释规则
```

真正的自然语言教学仍由 ChatGPT 完成。

## 13. “Learning OS”需要防止的五种跑偏

### 13.1 重新造 ChatGPT

不要自行建设通用聊天、普通语音、通用问答 Agent，只为了看起来像完整产品。

### 13.2 把网页变成主流程

结构化数据不意味着必须结构化网页。ChatGPT 里的自然问答同样可以通过 Tool 形成结构化 Evidence。

### 13.3 把状态当事实

不能为了快速显示一个“掌握度”而丢掉原始 Evidence。

### 13.4 Skill 膨胀成 Agent 平台

只有流程纪律会影响学习事实时才需要 Skill。普通解释、聊天和简单追问继续交给 ChatGPT 自然完成。

### 13.5 MCP 膨胀成数据库 API

MCP 工具数量少而语义强。每个工具应该对应一个稳定业务动作，不对应一张表。

## 14. M0 在这个架构中的位置

M0 实际只验证 Learning OS 最核心的一个最小回路：

```text
Context（可以先很薄）
→ ChatGPT 教学
→ Assessment Skill
→ 3 次真实回答
→ Evidence 写入
→ ChatGPT 继续教学
```

再额外选一个确实需要专用 UI 的 Activity，验证 Adapter 路线可用。

M0 不需要：

- 完整 Learner State；
- 完整课程图谱；
- 自动复习算法；
- 自研 AI Teacher；
- 复杂家长端；
- 多 Agent 编排平台。

## 15. 判断一个新功能是否属于 Learningflow

以后提出任何功能，先问三层问题：

```text
1. ChatGPT 自己已经能很好完成吗？
   是 → 默认不重做。

2. ChatGPT 做得到，但缺长期事实、约束、调度或可靠恢复吗？
   是 → 应该进入 Learningflow Runtime / Skill / MCP。

3. ChatGPT 缺少当前输入输出媒介吗？
   是 → 增加最小 Activity Adapter。
```

只有这三层都解释不清楚的功能，才需要重新讨论是否属于 Learningflow。
